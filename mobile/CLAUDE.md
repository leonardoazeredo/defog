# Cross the Fog (Expo app)

Read `AGENTS.md` first: Expo APIs change every SDK, so fetch the versioned docs (`expo` is `~58`, `https://docs.expo.dev/versions/v58.0.0/`) before touching an Expo, EAS or React Native API.

Android only. iOS is paused until the Android phone app and the Wear OS app are done, tested and released: no iOS builds, simulator runs, fixes or plan items before then, and every check runs on Android. `AGENTS.md`'s iOS examples do not apply.

## Commands

- Unit tests: `pnpm test` (vitest, projects `unit` and `adapter`). One file: `npx vitest run test/unit/incoming.test.ts --reporter=dot`.
- Typecheck: `pnpm typecheck` (it runs `pnpm generate` first). Lint: `npx biome check <paths>`; existing warnings in `test/adapter/hooks.test.ts` are unrelated.
- Full gate: `pnpm verify`.
- Builds: use `pnpm android`; it regenerates the web bundle first. A raw `npx expo run:*` does not.
- Android builds need JDK 21 (`JAVA_HOME=/Library/Java/JavaVirtualMachines/temurin-21.jdk/Contents/Home`), `ANDROID_HOME=$HOME/Library/Android/sdk`, and `--device <AVD name>`, not the adb serial.
- e2e builds need `CROSSFOG_E2E=1` for the web build, the app config and the prebuild, and a Release configuration. Run Maestro against them with `maestro --device <serial> test .maestro`.
- Pull requests: `gh pr create --repo leonardoazeredo/defog --base main`.
- `modules/watch-link` (Kotlin local module, hand-written and committed, unlike the generated `mobile/android/`; Gradle runs in `mobile/android` and finds it as project `:watch-link`). With the Android env above, in `mobile/android`:
  - JVM tests (`KeyWrapTest`, `KekReadTest`, `KeyStateTest`, `DatabaseKeyHexTest`, `StagedActivitiesTest`, `ModuleFailuresTest`, no device): `./gradlew :watch-link:testDebugUnitTest`.
  - Instrumented tests (`KeysTest`, real AndroidKeyStore; the AVD `chase-cashew-test` must be running): `./gradlew :watch-link:connectedDebugAndroidTest`. They run in the module's own test APK (its own UID, Keystore and `noBackupFilesDir`), so they never touch the installed app's keys.
  - `StagingStoreTest` and `FramesTest` (software key, no device) run under the same `:watch-link:testDebugUnitTest`; `StagingStoreKeystoreTest` (the real Keystore key) under `connectedDebugAndroidTest`. Set `ANDROID_SERIAL=emulator-5554` when a phone or watch is also attached.
  - Neither runs in `pnpm verify`.
- Kotlin keys: `Keys.databaseKey()` reads `noBackupFilesDir/keys/db.key.v1`; a file without the Keystore alias (or the alias without the file) is `KeyLostException`, and so is an `UnrecoverableKeyException` on the alias that repeats after one retry 200 ms later; JS sees either as `KeyLostError` from `src/platform/watchLinkModule.ts`, the only file meant to import the native module `modules/watch-link` (nothing enforces it), apart from `src/dev/devActions.ts`, which imports it directly so a static wrapper does not put `stageForTest` in the release JS. `keyState()` reads `fresh` (neither), `lost` (exactly one; an AtomicFile `db.key.v1.new` left by a kill before its rename does not count as the file), `unreadable` (both present, and the unwrap fails for good: `AEADBadTagException`, `KeyPermanentlyInvalidatedException` or a key of the wrong length, `KeyLostException.permanent`) or `existing` (both present and not failed for good: a repeated `UnrecoverableKeyException` or a busy Keystore still reads `existing`, so it may still fail; branch on the `getDatabaseKeyHex` rejection). Treat "fresh" as safe only when no database file exists. `resetKeys()` drops the Keystore key, `db.key.v1` and a stray `db.key.v1.new` so the next read mints a key; it refuses (`KeyRefusedException`, `ERR_INVALID_STATE`) while `filesDir/SQLite/crossfog.db` or `crossfog.replaced.db` exists or the state reads `existing`, and never touches the staging key. `openHistory` calls it when the state reads `lost` or `unreadable` and no database file exists (#72, #67), and reports `keyLost` for either state when one does.
- Native failure codes (`ModuleFailures.kt`): every call on a key (`getDatabaseKeyHex`, `keyState`, `replaceLostDatabaseKey`, `resetKeys`) answers `ERR_KEY_LOST` (`KeyLostException`), `ERR_INVALID_STATE` (only `KeyRefusedException`, a refused reset or replace), `ERR_INVALID_ARGUMENT` (a malformed key) or `ERR_KEY_UNAVAILABLE` (anything else: a busy Keystore, a failed file write), which `watchLinkModule.ts` turns into `KeyUnavailableError`, never `KeyLostError`. Staging calls answer `ERR_UNREADABLE` (an item that is oversized or does not authenticate: `StagingStore.read` throws `UnreadableItemException` and returns null only for an absent item), `ERR_STORAGE` (any other `IOException`; only its class is logged, since a path names the id), `ERR_INVALID_FRAME`, `ERR_INVALID_ID` or `ERR_NOT_FOUND`; anything else is rethrown as itself.
- Database key in JS (`src/db/keyHex.ts`): a key is a `DatabaseKeyHex`, a branded string only `checkedKeyHex` (64 lowercase hex digits, else "malformed database key") and `newDatabaseKeyHex(randomBytes)` (32 bytes, wiped after) make; `getDatabaseKeyHex`, `replaceLostDatabaseKey`, `openHistory`'s `openDriver`, `ReplaceDeps` and `createExpoSqliteDriver` take or return it, and the module and the driver check it again at run time. A key that reads but does not open the file (`NotADatabaseError`, a wrong key or a file that is no database, which the driver's main open also throws) reads as `keyLost` through `wrongKeyAsKeyLost` in `createDatabase` on every open; on the first open of a process with a replaced copy beside the live file, that copy is put back and opened before a wrong key is read as `keyLost`. A close that fails after a failed open or migration logs its error class; the first error is the one thrown.

- Staging: activities the watch hands over wait in `noBackupFilesDir/staging/<activityId>.bin` and queued routes in `noBackupFilesDir/outbox/<routeId>.bin` (AES-GCM under the Keystore key `crossfog.staging.v1`, id as AAD; both are `StagingStore`s). The TS side is `src/link/` over `src/platform/watchLinkModule.ts`; `createFakeWatchLink()` stands in for tests. Like the native side, its `release` refuses an id that is not a UUID ("invalid id"). `stageForTest(offerJson)` is registered only by the `src/debug` source set (the `src/release` twin is empty), so it is absent from a release dex; check with `unzip -p <apk> 'classes*.dex' | grep -a -c stageForTest`. A staged item that does not authenticate or parse (or whose offer names another id) is skipped by `pendingActivities`, never deleted, and counted by `unreadableActivities` (`readStagedActivities` in `StagedActivities.kt`); the hand-off adds the walks whose GPX fails `parseGpx`, `createFlows` sends the total as `unreadableActivities {count}` when it changes (and again on `ready` while above 0), and the History tab says "N walks could not be read." (#79). A lost staging alias is minted again rather than refused, since refusing would turn away every new walk; `Keys.stagingKey(sealedDirs)` logs a fixed line when it does so while `staging/` or `outbox/` holds a `.bin`, and the old items show in that count (#85). Outbox items under a lost alias are not counted.

- History store (`src/db/schema.ts`, `src/history/`): `migrate` runs every pending step in one transaction, so an interrupted open (even a killed process) leaves the old schema whole and the next open starts again. Schema 2 keeps an activity's GPX as `activities.gpx_deflated` (zlib BLOB, fflate's `zlibSync`, `src/history/gpxBlob.ts`); `ActivityStore` deflates on `add`, `get` returns the row without its GPX, and `gpx(id)` inflates it on demand. Route GPX stays text. `RouteStore.list()` returns `RouteSummary` rows, a `Pick` of the named fields (a new route field stays out of lists until it is added there and to each store's `list`), and `markSent` on an id it does not hold throws `UnknownRouteError` (the id is a property, never in the message) in both stores. `test/support/schemaV1.ts` builds schema-1 databases for tests (a restore test copies one in as an old backup).

- Backup and restore (`src/backup/`, `src/flows/backup.ts`, `src/platform/backupPlatform.ts`): a backup is a SQLCipher file made by `SqlDriver.exportTo` (`ATTACH ? AS backup KEY ?` with both bound, never spliced, then `sqlcipher_export`; key `null` is the plaintext copy after the P5 warning), reopened through `OpenBackup` to add `blobs` rows (`import` = the Fog of World zip, `page_settings` = the page's `f2m_*` keys), saved by the native `createDocument` + `copyToUri`, and removed from the cache in `finally`. Restore copies the picked document into `cache/backup/` with `copyFromUri` (it returns the first 16 bytes: `SQLite format 3` means a plaintext backup, anything else page-aligned may be encrypted), opens it, asks for confirmation, then `createDatabaseReplacer` closes the live database, exports the backup into `crossfog.restoring.db` keyed with the device key (when the key cannot be read and `keyState` reads `lost` or `unreadable`, with a new key generated in JS that `replaceLostDatabaseKey` keeps only after the swap and before the reopen, so a failed build leaves the old key and a failed reopen after it is kept leaves the new file live, since neither key opens the old one; a key that cannot be read while the state reads `existing`, such as a repeated `UnrecoverableKeyException`, ends the restore before the build), checks the counts, swaps files keeping `crossfog.replaced.db` until the new file has opened and migrated; `createDatabase` puts the old file back whenever a swap left no live one, and on the first open of a process keeps the replaced copy until the live file opens (putting it back if opening throws; a key-lost result leaves it beside the live file). A restore that cannot replace the saved fog still reloads the page (`fogNotReplaced`), and the controller refuses an import, a clear or a shared file while a restore runs. `createFlows` runs the whole restore under `HandOffFlow.hold`: no watch offer starts, an activity that commits meanwhile keeps its staged copy, and the hand-off runs again when the restore ends. `historyGate` (`src/db/gate.ts`) makes every store call shared and the swap exclusive. The page's settings travel as `needSettings` / `settings` and `applySettings` / `settingsApplied`; the restore waits for the ack before it reloads the page. `NotADatabaseError` cannot tell a wrong passphrase from a file that is no database, so the copy says both. `test/support/nodeSqliteDriver.ts` simulates keys per file path (node:sqlite cannot encrypt): the emulator is the real check, and `head -c 16` of the saved file is `SQLite format 3` only for an unencrypted backup. `createDocument` needs a person at the picker, so `SaveAsTest` covers the two copies on `file://` targets.

- Expo driver queue (`src/platform/expoSqliteDriver.ts`): `exec`, `run`, `all`, `transaction`, `exportTo` and `close` share one queue, because `withExclusiveTransactionAsync` uses its own connection and a plain query beside it fails with "database is locked"; a transaction callback must query only through its `tx` (a call on the driver from inside it waits on its own transaction forever, undetected), and a hung callback stalls every query. The node test driver does not queue plain queries.

- Backup passphrase rules: the backup dialog (`src/ui/passphraseForm.ts`) rejects a passphrase under 8 characters and one of the form `x'<64 hex>'` or `x'<96 hex>'` (any case; SQLCipher takes it as the raw cipher secret, with no derivation step), both with plain copy; a restore accepts any non-empty text.

- Exports (`src/flows/exportFlow.ts`, `src/platform/{zipWriter,exportFiles,crashLog}.ts`, page: `fowExport.js`, `exportWarning.js`): the page writes the Fog of World tiles and sends them as `exportBinary` chunks (1 MiB raw at most, `exportId` is `[A-Za-z0-9-]` and `name` is `[a-z0-9]`, both because they become path segments; `files` is the count of files in the export, at most 65534, one under the ZIP64 sentinel). `createExportFlow` queues the chunks (WebView messages are not serialized, so "every file is complete" is seen once), keeps parts under `cache/export-<exportId>/parts/<name>/<index>`, joins a finished file into `Sync/<name>`, and when all `files` are in writes `Sync.zip` with `writeZip` (stored, fixed 1980 date so the zip's own headers say nothing about when it was made; the suggested file name still carries the day), saves it with `saveFileAs` (`createDocument` + `copyToUri`) and removes the directory in `finally`; a cancelled picker says nothing, a disagreement between chunks or any error drops the export with a message that carries no path and logs the stage it failed in (`failed while receiving|assembling|zipping|saving`, then the class). The page is told each outcome as `exportStatus {exportId, state}`: `saving` just before the picker opens, then `saved`, `cancelled` or `failed` (`FowExport.button` in the page holds its button until one of the last three). An export with no chunk for `EXPORT_IDLE_MS` (60 s, armed after each handled chunk and run through the queue, so chunks still queued re-arm it first) is failed and its directory removed, with the fixed log line `export idle, dropped`; `abandon(exportId)` (a chunk of it failed the bridge's schema) does the same, and is a no-op for an export already finished or failed. Up to 256 finished or failed ids are remembered, so a late chunk does not start an export again. The next start removes any `export-*` directory (`ExportFs.removeExportDirs`) and `cache/exports/` (`clearShareCopies`). `exportFiles.ts` refuses a cache path with an empty, `.` or `..` segment, and `writeZip` an entry name with one (a leading `/` included) or a repeated name. `test/unit/bridge/exportLimits.test.ts` ties the page's `CHUNK_BYTES` to `EXPORT_CHUNK_BYTES`, `EXPORT_MAX_FILES` to `zipWriter`'s `MAX_ENTRIES`, and checks that Fog of World's tile names pass the chunk schema. `shareExport` (GPX, KML) deletes its cache copy as soon as `shareAsync` returns or fails. `scrubCoordinates` in `crashLog.ts` replaces every decimal number with three or more places by `[n]` and every `file://` or `/data`, `/storage`, `/sdcard`, `/mnt` path (which carries the export id) by `[path]`, in the message and not in the timestamp that has three decimals itself. A throw from `status` or `notify` is logged by class and changes nothing (a saved export stays saved, a failed one is still removed). `removeExportDirs` tries every entry and rethrows the first failure, so the log names its class. Every cleanup (`clear`, the `finally` after a save, `clearShareCopies`, `shareExport`'s delete) logs only an error class and never turns a saved export into a failed one. The page's console lines print the reason or the error class only; `bench/export-warnings.test.js` scans `app/src/*.js` for a `console.*` call that names `why`, `explain`, `lat`, `lng`, `coords` or the like.

- Off-origin navigation: react-native-webview is deliberately unpatched and fails open when `decideNavigation` answers late, so the page must make no navigation but a link click. `test/adapter/links.test.ts` scans `app/index.html`, `app/src/` and `app/vendor/` for `<form>`, a `location` assignment, `<meta http-equiv=refresh>`, `formaction` and `.submit()`; a hit in vendored code is not patched but allowlisted in that test's `ALLOWED` with the reason it cannot leave the origin (none today). `installLinks` (`web-adapter/links.ts`) lets through only a `blob:` download and a link whose path and query equal the document base's and that carries a fragment (`href` starting with `#`, or a non-empty hash; `href=""` or `"?"` is a reload and is stopped); every other same-origin link, whatever its `target`, is `preventDefault`ed and opens nothing, so it never reaches the late native answer. `window.open` and the click path share one resolver (`new URL` against the document base: `HTTPS://x` and `//x` open outside, an empty URL or a relative one on the origin does nothing), and `auxclick` is handled for the middle button only. `openExternal`, and the `external` navigation and `onOpenWindow` paths (`createLinkHandlers`, `src/bridge/linkHandlers.ts`, used by `WebShell.tsx`), go through `openLink` (`src/bridge/openLink.ts`): a rejected `Linking.openURL` logs the error class only and shows `COPY.openLinkFailed`, never the URL.

- Native-to-page messages: every one goes through `createSend` (`src/bridge/send.ts`), never a bare `postMessage`. It posts and then schedules a no-op `setTimeout(0)`. Expo Modules v2 (expo-sqlite, expo-crypto; `ReactJSScheduler.post` in `expo-modules-v2-react`) settles promises with `runOnJSQueueThread` plus a microtask drain, outside React Native's RuntimeScheduler. A WebView command issued there waits in the scheduler's rendering updates until the end of the next task, so without the timer it reached the page only when the page next posted (#139). A microtask does not release it; only a new task does. A debug build can hide this, so check native-to-page changes on a Release build (`.maestro/history-release.yaml`).

- Page-to-native messages: `WebShell` checks each with `inspectWebToNative` (`src/bridge/protocol.ts`); a message that fails the schema goes to `reportDropped` (`src/bridge/dropped.ts`), which logs its type (only a type the app knows, else `unknown`) and the zod issue paths, never a value, and answers a dropped `sendRoute` whose route id is a valid UUID with `routeStatus failed`; a dropped `exportBinary` whose `exportId` is valid (`DroppedMessage.exportId`) abandons that export, which answers `exportStatus failed` unless the export already finished or failed. A `needTrack` that passes the schema always gets an answer: the track, or `trackUnavailable` (`notFound`, `readFailed`); a dropped one gets none. So the page also times out the track request and the route send on its own (`REPLY_TIMEOUT_MS` in `app/src/history.js`), and the export (`REPLY_MS` in `app/src/fowExport.js`).

- Flow failures: every flow and the import log through `warnClass` (`src/flows/warn.ts`, the error class only). A history list that cannot be read sends `notice` `COPY.historyListFailed`, since the page keeps its last list (a deleted row included), except for `HistoryKeyLostError` (`src/db/openHistory.ts`, what `historyStores` throws while the key is lost; the startup alert already said so). `ImportFlow` does not reject on a store, picker or remount failure: a store failure ends any import it started, clears busy and says `COPY.importFailed` (a share that fails before it takes the import leaves a running one alone), with no remount after a failed promote or discard (a discard that failed would hand the page the same bad copy again). The import flow queues a notice (`queueNotice`, shown at the next `ready`) only when a `ready` will follow; its other failures are toasts (`notify`). The history may reach the page before or after the fog's `loaded`; the page's `FogMap` merges activity cells and imported tiles in either order (`bench/fog-map.test.js`).
- Page API (`web-adapter/pageApi.ts`): `PAGE_EVENTS` is the one list of native-to-page events; `isPageMessage` is what `session.ts` routes by, so a new event is added there only and the session cannot forget to route it (the page still needs its forward to `window.CrossfogPage` in `web-adapter/index.ts`, as `exportStatus` has). A route the page sends is bounded: `gpx` 10,000,000 characters, 100,000 coords, 500 waypoints; export chunk data is padded base64 of at most 1 MiB decoded.

## Tracked bundle

`generated/web.ts` is tracked. A `CROSSFOG_E2E=1` build or `pnpm generate` regenerates it, and the e2e flavour contains the developer-only "Dev: drop fog cache" button. After any e2e build run `git status --short` and restore it with `git checkout -- generated/web.ts`. Stage files by name, never with `git add -A`.

## Build and Maestro gotchas

- Gradle does not track `generated/web.ts` (it sits outside `mobile/`), so `createBundleReleaseJsAndAssets` can report `UP-TO-DATE` and ship the previous bundle. Before an Android build that changes the bundle (normal and e2e, either way, or an adapter change) run `rm -rf mobile/android/app/build/generated/{assets,res,sourcemaps}/react/release`, and check the build log shows the task ran. Hermes keeps some strings as UTF-16, so grep an APK bundle with `grep -a -c -P` on the spaced form.
- `android-mcp`'s device-side helper holds the UiAutomation connection, so Maestro fails with "Android driver did not start up in time". Kill the `com.wetest.uia2.Main` process on the device before a Maestro run; the next `Snapshot` restarts it.
- Maestro reports off-screen web view text as visible, so do not guard a swipe with `notVisible`. Use a fixed swipe, and assert that the app was left with `notVisible: "Expand or collapse panel"`.

## Tools

- Expo docs, EAS build status: the Expo MCP (`read_documentation`, `search_documentation`, `build_list`). Its builds run in the cloud and do not drive a local emulator.
- Android: `android-mcp` for the UI (never `adb shell uiautomator dump`, it crashes the service), and `adb`, the emulator and Gradle for builds, logs and root. There is no Android Studio MCP.
- Build and test output is large. Save it to a file and read `tail`/`jq` slices.

## Commit hook

A hook blocks `git commit` while comment-like lines are unreviewed (markdown, text and lockfiles are exempt). A new Maestro flow with no `#` lines still needed a review (probably because of the YAML `---` separator, which starts with `--`). Finish the edits, run the `pr-review-toolkit:comment-analyzer` agent alone with the first prompt line exactly `Repository: /Users/leo/Lab/defog`, wait for its report, re-run it if you changed a comment, then commit in a following turn. Do not bypass the hook.

## Private data

The owner's real backup (`Sync.zip`) is location history. Load it only on a device or through the page's own file input; never upload, commit or paste it.
